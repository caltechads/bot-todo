Scope and evidence

The audit covered the complete src/bot_todo package (7 modules, 6199 lines), the complete test suite (12 files, 5686 lines), all 11 architecture decision records, the packaging and build configuration, the repository's own agent instructions, and 42 commits of Git history spanning 12–26 August 2026. Framework detection identified a single pyproject.toml at the repository root with no Django, Qt or aiohttp signals, selecting the generic Python stack pack.

Evidence sources available: Graphify (refreshed at audit start — see Coverage limits), local Git history, and the project's own .venv tooling (pytest 9.1.1, mypy 2.3.0, ruff 0.16.2). Unavailable: CodeGraph (no index), code-index (installed as a uv tool but no MCP server exposed in this session), radon, and coverage.py/pytest-cov. Each unavailability, the substitute method used, and its precise scope are stated in Coverage limits rather than glossed.

Delegated analysis. Five units exceeded what could be read fully in the audit's own working context without displacing the rest of the work, and each was analysed by a dedicated subagent that read its target in full and returned a compact structured record; the full analyses were written outside the audited repository. The delegated units were: repository.py (1775 lines), cli.py (1672), web.py (1415), config.py + skill_installation.py (1283 combined), and the entire quality and test-suite pass (12 test files, all tool runs, all three mandatory test-organization checks). Every delegated claim carried forward into this report was re-verified against the source or by direct execution. That verification changed four claims materially: a reported claim traceback is in fact a clean coded error (F-14); a reported configuration-corruption risk does not corrupt the file, because the validating re-parse precedes the write (F-03); AggregateRunner's module placement is a decision recorded in ADR 0011 rather than a smell (F-21); and the v1→v2 format decision is recorded, in ADR 0006, so only one ADR sentence is stale (F-27). One subagent also reported and corrected its own invalid first mutation battery, documented in Coverage limits.

Repository integrity. The audit modified no source, test, documentation, packaging or configuration file — verified by git status over src, tests, docs, pyproject.toml, Makefile, README.md, AGENTS.md, CONTEXT.md, etc and bin after all five delegations completed. Two changes to the working tree are disclosed for completeness: files under graphify-out/ were rewritten by the authorized graph refresh described in Coverage limits, and TODO.md carried an uncommitted modification that predates this session. Verification that required writing — scratch task repositories, mutation copies, the 400-task pipe test — was performed entirely outside the repository.

Evidence labels. Every claim in this report carries one of three classifications. Observed locally is supported directly by a file, a line, a test result or a command's output. Verified externally is supported by an authoritative external source. Inference is a judgment drawn from stated observations. Candidate decisions lacking external verification are marked unverified and no adoption is recommended on their strength.

This is a well-built codebase with an unusually disciplined documentation and decision record, and its problems are concentrated in three places rather than spread thin. The module-level architecture is genuinely sound: the import graph is a clean acyclic layering with repository.py as a leaf domain module, the dependency manifest is exactly conformant in both directions (portalocker is the only third-party import in src and it is declared), mypy --strict reports zero errors across 19 files, the mandated documentation contract passes with zero violations and an empty baseline, and the test suite is fully order-independent and hermetic across six different execution orders. A complete escaping audit of the web layer's ~30 interpolation sites found no XSS defect, and its security controls — constant-time CSRF comparison, exact Host and Origin checks, loopback-only binding, fail-closed origin handling — are correctly implemented.

  • The single highest-leverage fix is the quality gate itself (F-07). [tool.ruff] declares only target-version, so the green lint result reflects four default rule families; the complexity family is unconfigured, which is exactly why a McCabe-26 function went unflagged. ruff and mypy have no Makefile targets despite being mandated after every change, the napoleon gate invokes a script in the maintainer's home directory and so cannot run from a clean clone, and there is no CI of any kind. Until this is closed, every other fix in this report can silently regress.
  • 93.2% line coverage conceals 71.4% error-path coverage (F-04). Of 112 raise sites, 48 never execute; nine of those were confirmed by mutation, including five invariants of the document validator and a guard whose test is named for the behaviour it does not check. The cause is structural: 79.5% of tests reach the code through the CLI or a socket, and both front doors flatten distinct errors into one shape (F-10).
  • Three reproducible defects were confirmed by direct execution. A broken pipe on successful output escapes as a traceback because one line sits outside the error guard (F-01); a repository path containing a control character produces an uncaught TOMLDecodeError instead of a JSON error document (F-03); and no read command works at all on a read-only repository, because the shared read lock is opened for append (F-13).
  • One duplication is byte-identical and has already drifted (F-02). config.py:693-724 and repository.py:1658-1690 are character-for-character the same except that the config copy lost the directory fsync — so configuration writes are not crash-safe while task-file writes are.
  • The repository's own architecture policy is the most-violated rule in it (F-08). AGENTS.md mandates cohesive classes over masses of free functions; repository.py and config.py hold 40 module-level private functions between them, 34% of one file. Notably web.py and skill_installation.py already conform, so the policy is achievable here.
  • Two thirds of the test suite's wall time is one default argument (F-15). The suite takes 39s wall but only 3.6s of CPU; serve_forever() at tests/test_web.py:38 uses the stdlib 0.5s poll interval, costing ~26.5s in teardown across 54 web tests. One keyword argument returns the suite to roughly 14s.

Build-vs-buy outcome. Six candidates were researched against concrete local targets. Only two are recommended, and both are standard library (hashlib.file_digest, enum.StrEnum) — no new third-party dependency is warranted anywhere in this codebase. Ten further candidates were evaluated and rejected without reaching a comparison row; all are enumerated under Kept deliberately rather than silently dropped.

03

Architecture map

Layering is sound; the problems are inside modules and across duplicated code, not in the dependency structure. repository.py imports nothing from its own package and is the leaf domain; config.py and skill_installation.py depend only on it; web.py adds config.py; cli.py sits on top of everything. There are no cycles, and mypy strict resolves cleanly — a real strength worth preserving through the extractions recommended below.

Graphify's refreshed graph (1434 nodes, 2761 edges, 83 communities) ranks the cli.py community lowest in cohesion at 0.06 and the repository.py community next at 0.05. Direct reading confirms the cause in both cases: in cli.py, six layers — parser policy, selector resolution, command orchestration, aggregation, presentation and process contract — share nothing but the TodoError type; in repository.py, a third of the file is a free-function block outside any class.

F-01

Successful output is written outside the error guard, so a broken pipe escapes as a traceback

Priority: High Confidence: High correctness Observed locally Effort: XS (1-line move)

Local evidence

  • cli.py:1671 — writer.success(...) sits after the try block that ends at line 1670
  • cli.py:1364 — print(json.dumps(document, ensure_ascii=False)) — the raising call
  • cli.py:1665-1670 — TodoError and OSError are both handled, but only for the pre-output phase

Impact scenario

Reproduced during this audit against a 400-task repository (202 354 bytes of JSON). bot-todo --json list | head -c 1 exits 1 with BrokenPipeError: [Errno 32] Broken pipe on stderr and no JSON envelope on stdout. Any agent that pipes a large query into a short-lived reader — head, jq -e with early exit, a closed subprocess pipe — receives a Python traceback instead of the documented machine-readable error document. The failure only appears once output exceeds the 64 KiB pipe buffer, so it is invisible in small repositories and appears as collections grow.

Recommended direction

Move the writer.success(...) call inside the existing guarded region so the established OSError → io_error path at cli.py:1668-1670 covers output as well as computation.

Migration outline

1. Move line 1671 above the except clauses, returning the exit code from inside the try. 2. Add a regression test that writes more than 64 KiB to a closed pipe and asserts a clean non-zero exit with no traceback. 3. Consider the same treatment for writer.failure at cli.py:1628.

F-02

Byte-identical durability helper duplicated across two modules, and the copy dropped the directory fsync

Priority: High Confidence: High correctness / duplication Observed locally Effort: S

Local evidence

  • config.py:693-724 — _replace_text — atomic replace, file fsync, permission preservation
  • repository.py:1658-1690 — _write_document — character-for-character identical including the docstring
  • repository.py:1690 — the one differing line: _fsync_directory(path.parent), absent from the config copy
  • config.py — grep fsync returns only line 718 (the file descriptor) — config.py never syncs a directory

Impact scenario

Verified by diffing both bodies: they are identical apart from the function name and that single trailing call (md5 of the two extracted bodies differ only on those two lines). The task-file writer deliberately flushes the parent directory entry so a rename survives a crash; the configuration writer does not. A power loss or kernel panic immediately after bot-todo repos add can therefore lose the configuration rename while an identical crash preserves the TODO.md rename — asymmetric durability produced purely by copy-paste drift, in a project that has an ADR about durable writes. There is also no durability test for config.toml: tests/test_repository.py:65-108 DurabilityTests covers the task file only.

Recommended direction

Delete one copy. config.py:14 already imports three names from bot_todo.repository, so the lazy fix is to import the existing writer rather than introduce a new module.

Migration outline

1. Delete config.py:693-724. 2. Import and call repository._write_document (or promote it to a small shared DurableTextFile collaborator if the private-name coupling is unwanted). 3. Extend DurabilityTests to cover config.toml so the two writers cannot diverge again.

F-03

Hand-rolled TOML escaping under-escapes control characters, breaking the --json contract with an uncaught traceback

Priority: High Confidence: High correctness / contract Observed locally Effort: S

Local evidence

  • config.py:651-668 — _toml_string escapes only \, ", \n, \t
  • config.py:483 — _document_entries(self.path, tomllib.loads(text)) — not wrapped, unlike config.py:201-204
  • config.py:301-302, 488-527 — repository paths carry no character validation, unlike names (NAME_RE, config.py:32)
  • cli.py:1665, 1668 — main catches only TodoError and OSError

Impact scenario

Reproduced end to end during this audit. tomllib rejects raw \r, \x0c and other C0 control characters in a basic string, which was confirmed directly against the exact _toml_string implementation. Adding a repository whose POSIX path contains a carriage return (bot-todo repos add "$PWD/ba"$'\r'"d") produces an uncaught tomllib.TOMLDecodeError: Illegal character '\r' traceback and no JSON error document, defeating the machine contract that every agent consuming this CLI depends on. The existing configuration file is not corrupted — the validating re-parse at line 483 runs before the write at 484, so the prior good file survives and remains readable. The severity is contract violation and unhandled-exception surface, not data loss.

Recommended direction

Escape the full set of TOML-illegal control characters and wrap the validating re-parse so any residual decode failure surfaces as a coded TodoError. Adopting a TOML-writer dependency is not warranted — see the build-vs-buy matrix.

Migration outline

1. Extend _toml_string to emit \u00XX escapes for all C0 controls plus \r and \x7f. 2. Wrap config.py:483 in try/except tomllib.TOMLDecodeError raising TodoError(..., "invalid_config"). 3. Add a parametrized test over the control-character class — the existing test_quotes_in_paths_are_escaped (tests/test_collection_store.py:213) covers exactly one character and its generalizing name invites the wrong conclusion.

F-04

93.2% line coverage conceals 71.4% error-path coverage: 43% of raise sites never execute

Priority: High Confidence: High test-coverage Observed locally Effort: L

Local evidence

  • src/bot_todo/*.py — 112 raise sites and 33 except handlers; 48 raises (43%) and 10 handlers (30%) never execute under the suite
  • repository.py:1336-1345, 1350-1351 — invalid/duplicate task ID, one-type-tag, repeated-tag, acceptance-or-simple — all mutation-confirmed dead to the suite
  • repository.py:1354-1366 — the entire closed-task branch of the validator, 5 invariants, never exercised
  • repository.py:849, 875, 1599 — double-claim, release-unclaimed, transition-on-closed — message strings appear nowhere in tests/
  • repository.py:1428-1429 — malformed-Claimed guard is unreachable behind _require_text (1347), yet tests/test_cli.py:310 is named test_validate_rejects_blank_field_and_malformed_claim

Impact scenario

38% of all uncovered lines sit on error paths that make up only 9% of the code. Gaps were confirmed by targeted mutation against a scratch copy of the tree: gutting each guard left the suite at 285-287 passing. The concrete risk is that the validator — the component that decides whether a repository's canonical file is trustworthy — can regress silently in five of its invariants, and that a test name asserts a guarantee the test body does not check. The root cause is structural, not negligence: 79.5% of tests reach the code through the CLI or a socket, and both front doors flatten distinct errors into one shape (config.py has 10 raises all coded invalid_config, and 11 tests assert only that code; web.py has 8 usage raises all rendering as 400 Bad request).

Recommended direction

Add a direct unit tier for the two pure validators (_validate_document, _validate_claim) and assert on error identity rather than error class. Parametrizing the existing collapsible clusters (F-23) is the cheapest vehicle, because it converts assertEqual(code, 'invalid_config') into (input, expected_message) pairs in the same edit.

Migration outline

1. Add tests/test_document_validation.py calling _validate_document on hand-built hostile documents, one parametrize entry per raise site. 2. Change the 11 code-only assertions in tests/test_config.py to assert messages. 3. Delete the unreachable guard at repository.py:1428-1429 and rename tests/test_cli.py:310 to match what it verifies. 4. Track the error-path figure (71.4%) rather than the line figure as the gate.

F-05

The Kanban edit path's field validation is entirely untested while the identical add path is covered

Priority: High Confidence: High test-coverage Observed locally Effort: S

Local evidence

  • web.py:539-542 — edit_task unknown priority / unknown task type — mutation-confirmed never executed
  • web.py:493-496 — the character-equivalent checks in add_task — these are tested
  • web.py:545-553 — the adjacent acceptance/simple and reserved-tag rules on the edit path, also untested

Impact scenario

Gutting the edit-path guards left the suite at 285 passed. Because the add path is symmetric and covered, a reader auditing web.py sees a validated edit path that is not actually verified; a refactor that drops or inverts these checks ships green. The consequence is that a crafted board POST could write an out-of-range priority or an unrecognized type tag into TODO.md, which the repository layer does not independently reject — repository.py:793-795 indexes document.active[priority] directly and would surface a raw KeyError rather than a coded TodoError.

Recommended direction

Mirror the existing add-path tests onto the edit path, and push the priority/type membership rule down into RepositoryTransaction so it is enforced once rather than in three adapters.

Migration outline

1. Copy the add-path validation tests in tests/test_web.py, retargeting /tasks/<id>/edit. 2. Add a domain guard in repository.py converting an unknown priority into TodoError(..., "usage"). 3. Consider Literal["P0","P1","P2"] on the transaction signature so mypy catches the class statically.

F-06

_validate_document is simultaneously the most complex function and the largest untested branch cluster

Priority: High Confidence: High architecture / test-coverage Observed locally Effort: M

Local evidence

  • repository.py:1321 — McCabe 26 — 2.6× the next-highest function in its own file, verified via ruff --select C901
  • repository.py:1333-1389 — roughly 18 raise sites, of which about 15 never execute under the suite
  • pyproject.toml:52-53 — [tool.ruff] sets only target-version, so C901 never runs in the project's own gate

Impact scenario

This function's complexity is its branch count, and about 60% of those branches are invisible to the test suite. It is the single highest-risk unit in the repository: the widest decision surface, the least verification, and no lint rule configured that would have flagged it. Independent confirmation during this audit: enabling --select C901 with a threshold of 8 reports exactly 7 functions, headed by this one at 26.

Recommended direction

Extract a DocumentValidator class holding one invariant per method, which both lowers the per-function branch count and creates the seam that makes each invariant unit-testable. This is the clearest instance of the free-function-mass problem in F-09 and should be the first extraction attempted.

Migration outline

1. Introduce DocumentValidator with the document injected in the constructor; convert each raise group into a small named method. 2. Add one test per method (this closes most of F-04 as a side effect). 3. Enable lint.select with the complexity family so the ceiling is enforced afterwards (F-12).

F-07

The project's own mandated quality gate is under-configured, partly unenforceable, and has no CI

Priority: High Confidence: High process / policy conformance Observed locally Effort: S

Local evidence

  • pyproject.toml:52-53 — [tool.ruff] declares only target-version — no lint.select, so only default E4/E7/E9/F rules run
  • Makefile — no ruff target and no mypy target, though AGENTS.md requires both after every change
  • Makefile:61 — make napoleon-gate runs python ~/bin/check_napoleon_gate.py — a script outside the repository and outside any manifest
  • (repo root) — no .github/, no .pre-commit-config.yaml, no CI configuration of any kind
  • ruff format --check — 7 of 21 files would be reformatted while the gate reports green

Impact scenario

The repository's AGENTS.md mandates a three-part gate (ruff, mypy, napoleon-gate) after every implementation. Two of the three have no Makefile target, so they depend on an operator remembering the exact invocation; the third cannot run at all from a fresh clone because its checker lives in the maintainer's home directory. Nothing enforces any of it on push. The measured consequence is a gate that reports clean while E501, the entire complexity family (C901/PLR0912/PLR0915) and formatting are unchecked — which is precisely why F-06's McCabe-26 function was never surfaced. This is the highest-leverage finding in the report: it is small work that makes every other finding harder to reintroduce.

Recommended direction

Configure lint.select explicitly, add ruff/mypy/format-check Makefile targets, vendor the napoleon checker into bin/, and add a minimal CI workflow running the existing commands on the declared Python versions.

Migration outline

1. Add [tool.ruff.lint] select = [...] starting from the current-passing set plus E501 and C901, with a per-file ignore or an explicit baseline for the 7 known offenders. 2. Add make lint, make typecheck, make format-check. 3. Move check_napoleon_gate.py into bin/ and point the Makefile at it. 4. Add a CI job matrixed over 3.11-3.14 running make pytest lint typecheck napoleon-gate.

F-08

40 module-level private functions in the two core domain modules contradict the repository's own architecture policy

Priority: Medium Confidence: High architecture / policy conformance Observed locally Effort: L

Local evidence

  • repository.py:1168-1777 — 24 module-level private functions — 608 lines, 34% of the file, outside any class
  • config.py:179-746 — 16 module-level private functions, roughly 400 of 746 lines
  • AGENTS.md — “prefer cohesive, human-comprehensible classes over large collections of loosely related free functions, even when those classes are mostly stateless”
  • web.py / skill_installation.py — 0 and 1 module-level private functions respectively — these modules already conform

Impact scenario

This is the repository's own mandated pattern, checked exhaustively across all seven modules rather than noticed incidentally. The functions are not arbitrary: they cluster into five unnamed concepts in repository.py (Markdown codec, document validator, field-value rules, durable filesystem access, selection policy) and three in config.py (document validator, TOML writer, CLI path-name policy). Two measurable costs follow. First, the clusters thread implicit shared context as repeated parameters — four codec functions pass a source string that is really a missing constructor argument, and four selection functions all take document first. Second, the absence of a class boundary is why the validator has no unit tests (F-04, F-06): there is no object to construct and no seam to test through. The contrast with web.py and skill_installation.py, which conform, shows the policy is achievable in this codebase.

Recommended direction

Convert the clusters into classes incrementally, highest-value first: DocumentValidator (unblocks F-06 and much of F-04), then TaskDocumentCodec, then a shared DurableTextFile (which also resolves F-02). Leave the small field-value helpers as functions if no cohesive concept emerges — the policy targets masses with shared implicit context, not every standalone helper.

Migration outline

1. Extract DocumentValidator first and land its tests. 2. Extract TaskDocumentCodec holding the parse/render pair plus the source context. 3. Fold _write_document/_fsync_directory/_replace_text into one writer collaborator. 4. Re-run make napoleon-gate after each step; the documentation contract is currently fully satisfied and should stay that way.

F-09

Four god classes concentrate unrelated concerns, led by a 1060-line web application object

Priority: Medium Confidence: High architecture Observed locally Effort: L

Local evidence

  • web.py:81-1140 — KanbanWebApp, 1060 lines, 7 concerns including 646 lines (46% of the module) of hand-assembled HTML
  • cli.py:457-910 — CommandRunner, 454 lines: 16-way dispatch, 16 handlers, presentation literals, one business rule
  • repository.py:622-1006 — RepositoryTransaction, 385 lines, 14 responsibilities including clock and subprocess access
  • skill_installation.py:119-537 — SkillInstaller, 418 lines, 5 separable jobs
  • tests/test_web.py — 63.8 KB / 54 tests — the test file is larger than the module it tests, and 47 of those tests live in one class

Impact scenario

Graphify scores the cli.py community at 0.06 cohesion and the repository.py community at 0.05 — the two lowest in an 83-community graph — and direct reading confirms why: TodoError is the only thing the layers in cli.py share. The practical cost is comprehension and testability. KanbanWebApp mixes selection resolution, socket binding, repository mutation and markup generation in one object, so every board change requires reasoning about all four; its test file being larger than the module is the usual signature of a unit that cannot be tested in units. Replace CommandRunner's 16-way dispatch with a class-level command table, collapsing the 6 near-identical mutation handlers (cli.py:697-805, ~110 lines expressing 6 method names). 4. Split KanbanWebTests by concern so server-less tests stop paying for an HTTP server.

F-10

38 of 58 TodoError raises omit their error code, and the web layer branches on that code to choose an HTTP status

Priority: Medium Confidence: High correctness / contract Observed locally Effort: M

Local evidence

  • repository.py:1203-1451, 1514, 1549, 1569, 1626, 1634 — all parser and validator raises omit the code argument and default to invalid_document
  • web.py:1285-1288 — the POST handler branches on invalid_document to return HTTP 400 rather than 500
  • config.py — 10 raises all coded invalid_config; 11 tests assert only that code

Impact scenario

Because a malformed user submission and a corrupt on-disk file both arrive as invalid_document, the HTTP layer cannot distinguish “the operator typed something invalid” (400) from “this repository's canonical file is damaged” (500), and neither can an agent parsing the JSON envelope. This is also the mechanism that hides test gaps: when eight distinct raises render as one 400 Bad request, a test asserting the status passes no matter which raise fired, which is exactly how F-05 went unnoticed.

Recommended direction

Assign distinct codes to the user-input and file-corruption families, and assert on message identity rather than code in the tests that currently only check the class.

Migration outline

1. Introduce a code for submission-level validation failures distinct from document corruption. 2. Update web.py:1285-1288 to map the new code to 400 and leave invalid_document as 500. 3. Convert the 11 code-only assertions to message assertions. Coordinate with F-04, which touches the same tests.

F-11

646 lines of hand-assembled HTML defended only by roughly 30 manual escape calls and a docstring contract

Priority: Medium Confidence: High architecture / security-hygiene Observed locally Effort: M

Local evidence

  • web.py — 18 render methods, ~646 lines (46% of the module), f-string markup with no template layer
  • web.py:1101, 1105 — the “trusted markup” contract for _page(content=...) is enforced only by a docstring
  • web.py:785-792, 831-838, 950-956 — the same 8-line modal chrome duplicated three times
  • tests/test_web.py:238-263 — the only escaping test — title-in-card

Impact scenario

A full escaping audit of every interpolation was performed and no XSS defect was found: all roughly 30 sites escape, both free-form sources (Task.title and parsed field values) are escaped at every site, and there is no inline JavaScript or on* attribute anywhere in the file, which removes that bug class entirely. The finding is therefore about the safety margin, not a present hole: correctness rests on a human remembering html.escape at every one of thirty sites, on a trusted-markup convention that only a docstring states, and on a single escaping test. One missed call in a future render method is an injection, and nothing mechanical would catch it.

Recommended direction

Extract BoardRenderer with a single escaping chokepoint and add a per-field escaping test. A templating dependency (Jinja2, whose autoescape would make the trusted-markup contract machine-checked) is a genuine option but is blocked by ADR 0007's “no Python runtime dependency” clause — see the build-vs-buy matrix.

Migration outline

1. Extract the render methods into BoardRenderer with one escaping helper all markup must route through. 2. Add a test that submits a hostile payload into every persisted field and asserts it appears escaped in every surface (card, modal, detail, error page). 3. Collapse the triplicated modal chrome. 4. Only then decide the Jinja2 question, with an ADR either way.

The local web server sets no socket timeout, so an idle connection pins a thread indefinitely

Kept deliberately

Complete enumeration of what the audit examined and concluded should stay as it is. A retained implementation is an expected outcome of the capability pass, not a gap in it.

Bespoke Markdown task-file codec

repository.py:1168-1320, 306, 364

No standard-library or existing-dependency replacement exists. It is a line grammar with a byte-exact round-trip requirement frozen by ADR 0002. markdown-it-py, mistune and commonmark would each be a new dependency, would still need the grammar checking layered on top, and — decisively — provide no canonical serializer, so the render half stays hand-written regardless. re plus splitlines() is the right tool. The finding here is organization (F-08), not replacement.

RepositoryLock over portalocker

repository.py:457-543

Already the thin translation layer ADR 0001 prescribes, delegating timeout and retry to portalocker.Lock(timeout=..., check_interval=...). No hand-rolled retry loop exists anywhere in src, so tenacity and similar have no local target.

_fsync_directory

repository.py:1693-1713

No standard-library equivalent exists, and the Windows limitation is already documented in a ponytail: comment naming the exact weakened guarantee. Keep.

_validate_date

repository.py:1433-1451

Already built on date.fromisoformat, with a deliberate isoformat() re-check to reject non-canonical inputs such as 2026-8-17 that parse but do not round-trip. Correct as written.

Hand-rolled tree scan in _scan

skill_installation.py:244-276

Deliberate and correct: os.walk cannot abort on the first symlink, and filecmp.dircmp produces no persistable digest for an ownership manifest. Only the in-memory read (build-vs-buy row 2) should change.

Standard-library HTTP server

web.py:205, ADR 0007

An explicit, documented decision. Flask, FastAPI, NiceGUI and Starlette were considered and rejected in the ADR on dependency-weight and async grounds. The audit found the security controls implemented on top of it to be correct: constant-time CSRF comparison, 256-bit token, exact Host and Origin checks, fail-closed on empty origin, loopback-only bind, tight CSP, and headers applied through an end_headers override so even stdlib-generated error pages receive them.

Integration-heavy test pyramid

181 of 287 tests (63%) drive the real CLI against real files

A diamond with no base rather than a pyramid, and defensible for this system: bot-todo's contract is its CLI and its on-disk format, so mocking the filesystem would verify nothing. Fixtures are built by invoking the real init (tests/support.py:56), so they cannot drift from the production writer — a genuine strength. The cost is real and recorded separately as F-04: integration tests reach error branches only through a front door that flattens them.

Wheel-build end-to-end tests

tests/test_distribution.py, 2 tests, ~1.9s

The only verification that the package installs and its console script runs outside the checkout, and the only check that bundled skill assets actually ship. Worth its runtime. Noted limitation: it is uv-gated, so it is the first coverage to disappear on another platform.

AggregateRunner living in cli.py

cli.py:1112, ADR 0011:30

Explicitly considered and rejected for relocation in ADR 0011, on the grounds that its active-only machine/human output contract does not model recent Done work or browser mutations. Not a smell — a recorded decision. Only the narrow verbatim failure-aggregation copy (F-21) falls outside what the ADR settled.

Seven test files driving cli.py

test_cli.py (165 call sites) plus 6 others

Checked as possible fragmentation and found benign: each file owns a coherent slice, and test_web.py and test_repository.py use the CLI as a fixture builder rather than as subject. Naming discipline is good and there are no regression-artifact-named files anywhere in the suite.

The five ponytail: shortcut markers

repository.py:579, 984, 1704, 1733; web.py:252

Each names its own ceiling and upgrade path, which is the discipline these markers exist to enforce. The one with a genuine correctness window — the archive-append/task-file-replace crash gap at repository.py:984 — is covered by tests/test_repository.py:110. Keep as documented, accepted trade-offs.

Archive-overflow and ID-width boundaries

repository.py:51 DONE_LIMIT = 20, MIN_ID_WIDTH

Investigated as suspected untested boundaries and found genuinely well pinned: mutating DONE_LIMIT to 19 fails a test and to 21 fails five; mutating MIN_ID_WIDTH from 3 to 4 fails 22. An initial draft finding here was wrong and mutation testing corrected it.

Considered, not a real candidate (honest negative results)

  • platformdirs — Real local target (config.py:123-127) but skeptically rejected: 5 lines, a dependency, a macOS behaviour change breaking two tests, and it does not address the actually-weak precedence chain.
  • tomli-w — Real local target and a real local defect, but the defect is a closed, known escaping specification fixable in about 3 lines. A second runtime dependency is not warranted.
  • Jinja2 — Real local target (646 lines of hand-assembled markup) but blocked by ADR 0007's standing no-runtime-dependency clause, and the cheaper structural fix removes most of the risk. Not recommended without a superseding ADR.
  • Click / Typer — The CLI is already standard-library argparse. Seven of nine requirements are native; the two gaps are output concerns no framework addresses. No replacement target exists.
  • tenacity / retry libraries — No local target. Lock acquisition retry is already delegated to portalocker's own timeout and check_interval; grep found no hand-rolled retry or sleep loop in src.
  • cachetools / functools caching — No local target. No memoization, lru_cache or hand-rolled cache exists anywhere in src.
  • beautifulsoup4 / lxml — The only near-match the offline catalog returned. They parse HTML and XML; this project generates HTML and parses a bespoke Markdown grammar. Not a fit.
  • Markdown parser libraries — See Kept deliberately — no canonical serializer, so the render half would remain hand-written and the dependency would buy nothing.
  • coverage.py / pytest-cov — Genuinely missing from the dev dependency group and worth adding, but there is no hand-rolled coverage implementation to replace, so this is a test-evidence gap (see Coverage limits and F-07), not a build-vs-buy decision.
  • radon — Same routing: absent tooling, no local replacement target. Recommended as uv tool install radon so the maintainability index stops being unverifiable.

Coverage limits

What was checked, by what method, over what portion — and what specifically could not be established.

Graphify — available, refreshed

The graph was stale at audit start (graph.json dated 12 August against source and documentation changes through 26 August, 25 files newer). Rather than proceed against stale topology, the audit stopped and obtained authorization, then ran graphify update ., producing 1434 nodes, 2761 edges and 83 communities at commit 60143bd. Extraction quality: 91% extracted, 9% inferred, 0% ambiguous. Two non-source JSON files produced zero nodes and are absent from the graph (settings.local.json, napoleon_gate_baseline.json); neither affects the analysis. The refresh modified files under graphify-out/ only — see the integrity note in Scope and evidence.

CodeGraph — unavailable

No .codegraph/ index exists for this repository, so no source-level symbol and call-path index was available to sharpen Graphify nominations. Direct reading and grep were used instead, and every finding was verified against the source regardless.

code-index — actively attempted, unavailable

code-index-mcp v2.14.0 is installed as a uv tool, but no code-index MCP server is exposed in this session; a tool search for its set_project_path and build_deep_index entry points returned no matches, so it could not be initialized. Consequence and substitute: semantic near-duplicate detection across differently-named files was replaced by AST-normalized structural duplicate detection over all 12 test files and all 287 tests (not a sample), plus targeted grep and byte-level diffing across all 7 source modules. That substitute is what found the byte-identical duplication in F-02 and the five test clusters in F-24, so the gap is narrower than the missing tool implies — but a semantic index might have surfaced conceptual near-duplicates that share no tokens, and none of those can be ruled out.

Line coverage — measured, but not by coverage.py

coverage.py and pytest-cov are absent from .venv and undeclared in the dev dependency group, and installing them was out of scope. Coverage was therefore obtained by instrumenting the suite with the standard library's sys.monitoring, recording each line once: 93.2% (2374 of 2548 lines) over 100% of src, with error-path lines separately at 71.4%. This figure is line coverage only. Branch coverage was not measured and would be lower. Recommendation: add pytest-cov to the dev group so this is reproducible rather than reconstructed.

Per-test coverage attribution — unavailable

--cov-context=test requires coverage.py, so per-test line attribution could not be used for redundant-test detection. Substitute method and its exact scope: every one of the 287 test functions was parsed and its body normalized (literals erased) to find mechanically identical tests, yielding 5 clusters covering 17 tests. This finds literal-parameter duplication reliably; it does not find tests that cover the same production lines by different routes, which only per-test contexts would reveal.

Cyclomatic complexity — measured, but not by radon

radon is absent from .venv, $PATH, ~/.local/bin and uv tool list. Complexity was obtained instead from ruff's McCabe implementation (--select C901 with the threshold driven to zero), giving real per-function scores over 100% of src: 223 functions, mean 2.43, maximum 26. Independently re-verified during report preparation at a threshold of 8, which reports exactly 7 functions. This is genuine McCabe, not a grep proxy.

Maintainability index — unverified

This is the one metric that could not be closed. The maintainability index is a radon-specific composite of Halstead volume, cyclomatic complexity, source lines and comment ratio; ruff implements no equivalent and there is no standard-library substitute. No file was graded, and the count of files at the worst grade is unknown. Remedy before the next audit: uv tool install radon.

Mutation testing — deliberately partial

Test-gap findings were confirmed by hand-applied mutation against a scratch copy of the tree, not by a mutation-testing framework, and were targeted at roughly a dozen specific guards rather than the whole codebase. Nine gaps are labelled mutation-confirmed (guard removed, suite still green); the remaining gaps in F-04 rest on never-executed evidence only and are labelled accordingly. A methodological failure is worth recording: the first mutation battery was invalid because .venv/bot_todo.pth points at the real src, so mutants never loaded and every apparent survival was meaningless; it was detected by asserting __file__ and the mutated constant before each run, and re-executed under an explicit PYTHONPATH. Only corrected-battery results appear in this report.

External package health — unverified

The offline python-package-advisor catalog was consulted once per qualifying candidate with --role audit, as required, and returned no_match for TOML writing, platform config directories and CLI parsing, and needs_clarification resolving to an unrelated markup-parsing profile for the rest; the packaged catalog contains 9 profiles in total. No network verification of maintenance status, release cadence, advisories, licences or OpenSSF signals was performed for tomli-w, Jinja2 or platformdirs. No adoption is recommended on the strength of unverified evidence — the two adopt recommendations in the matrix are standard-library only.

Runtime matrix — single interpreter

Every command in this audit ran on CPython 3.14.3, the only interpreter in the project's .venv. The package declares support for 3.11, 3.12 and 3.13 and mypy targets 3.11, but none of those three was exercised and no CI configuration exists in the repository to exercise them. Behaviour differences on the declared versions are therefore unverified — a live concern, since cli.py:53-55 already branches on a 3.14-only argparse feature.

Not in scope

The following were deliberately not audited: the rendered contents of graphify-out/graph.html and GRAPH_REPORT.md as documents; the substantive correctness of the 42 specification and plan documents under .scratch/; visual comparison of the 3.4 MB of design PNGs (their presence and tracked status were verified, and all seven files referenced by design-qa.md exist); and the uncommitted working-tree modification to TODO.md, which predates this session. Isolated ruff and mypy findings are outside this report's remit by design and are reported only where they demonstrate a broader pattern — F-07 is the one place they do.
